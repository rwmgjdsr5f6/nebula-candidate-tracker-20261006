一、公开入口与调用链
--------------------------------------------------------------------------------

1. 命令行入口：python -m recruiting --db <文件> <子命令> ...
   [代码] recruiting/__main__.py:3-6
     from recruiting.cli import main
     if __name__ == "__main__":
         sys.exit(main())
   [代码] recruiting/__init__.py:3 导出 main（库入口存在，但本文只追踪
          命令行用法）。

2. main()：解析参数 → 连接数据库 → 分发 → 关闭连接
   [代码] recruiting/cli.py:392-398
     args = build_parser().parse_args(argv)     # cli.py:393
     conn = connect(args.db)                    # cli.py:394
     try:
         return args.handler(conn, args)        # cli.py:396
     finally:
         conn.close()                           # cli.py:398
   进程退出码即 handler 返回值（成功 0、业务校验失败 2），经
   __main__.py:6 的 sys.exit(main()) 成为命令行退出码。
   main 只有 try/finally，没有 except：业务之外的 sqlite3 异常会以 Python
   回溯抛出，不在本文描述的契约内。

3. 参数注册（build_parser，cli.py:335-389）：
   - 全局 --db 必填：cli.py:337 required=True。
   - 子命令必填：cli.py:338 add_subparsers(..., required=True)。
   - add（cli.py:340-344）：--name、--email、--position 三个选项均
     required=True（cli.py:341-343），无 --stage 选项。
   - list（cli.py:346-351）：--position required=True（cli.py:347）；
     --name、--stage、--email 均为可选且未设 default，省略时取值为
     None（cli.py:348-350）——这是“省略”与“显式空值”得以区分的
     解析层前提。

4. 两类不同的错误出口（细节见第六节）：
   - argparse 层：缺少必填的 --db/子命令/--position 等，由 argparse
     自行向 stderr 输出 usage 用法说明并以退出码 2 终止（parse_args 在
     cli.py:393，代码不捕获 SystemExit）；stdout 为空，不输出 JSON。
   - 应用层：字段校验失败由各 handler 输出 {"errors": ...} JSON 到
     stderr、返回 2，且不发生任何写入。

二、共享存储：add 与 list 通过同一个 SQLite 文件交换数据
--------------------------------------------------------------------------------

1. 本地 SQLite 文件（标准库 sqlite3）。[代码] cli.py:4 import sqlite3；
   connect()，cli.py:42-47：
     conn = sqlite3.connect(db_path)   # cli.py:44，文件不存在则创建
     conn.execute(SCHEMA)              # cli.py:45
     conn.commit()                     # cli.py:46
   SCHEMA 为 CREATE TABLE IF NOT EXISTS（cli.py:10-18），每次调用幂等
   建表。[文档] README:7 “首次操作时自动创建数据库文件与表”，一致。

2. 本流程唯一使用的表 candidates（[代码] cli.py:10-18）：
     id       INTEGER PRIMARY KEY AUTOINCREMENT
     name     TEXT NOT NULL
     email    TEXT NOT NULL
     position TEXT NOT NULL
     stage    TEXT NOT NULL
   除主键外没有 UNIQUE、CHECK、COLLATE 等约束（建表语句中不存在）。

3. add 保存与 list 读取的衔接：
   - add 校验全部通过后执行参数化 INSERT 并立即 conn.commit()
     （cli.py:76-81）；校验失败在 cli.py:72-74 提前 return 2，
     INSERT 语句（cli.py:76-80）根本不执行——登记失败不新增记录。
   - list 只执行 SELECT（cli.py:116-130），不含任何 INSERT/UPDATE：
     查询无论成功还是参数失败都不改记录。
   - 持久化机制（保存后重开同一数据库仍可取回）：每次
     `python -m recruiting` 都是独立新进程，main 用同一 --db 路径
     重新 sqlite3.connect（cli.py:394、44）；CREATE TABLE IF NOT
     EXISTS 对已有表是空操作（cli.py:45），此前 commit 的行仍在文件
     中，list 的 SELECT（cli.py:116-130）直接读出。
   [测试] test_add_registration.py:106-121 在登记进程结束后的另一次
   独立调用中 list 到同一记录，:123-146 重复登记后重启进程按 id 升序
   读到两条；test_list_filter.py:188-197 与
   test_list_name_filter.py:204-213 断言两次独立命令调用同一数据库的

三、登记流程 cmd_add（cli.py:60-91）
--------------------------------------------------------------------------------

1. 字段去两端空白（cli.py:61-63）：
     name     = args.name.strip()
     email    = args.email.strip()
     position = args.position.strip()
   库存值与后续校验都基于 str.strip() 后的字符串；strip 只去两端，
   不动内部空白。[文档] README:30 “字段两端空白会被去除”，一致。

2. 邮箱保留大小写：[代码] 全文件不存在 lower/upper 等大小写转换，
   email 按 strip 后原样保存（cli.py:62、79、86）。
   [文档] README:30 “邮箱保留内部大小写”，一致。
   [测试] test_add_registration.py:22 固定值 "Lin.Xiao@example.test"，
   :100-101 断言落盘与回显均保持该大小写（未运行）。

3. 校验（cli.py:65-74），错误收集进同一个 dict，键的插入顺序即
   判断书写顺序 name → email → position：
   - name strip 后为空     -> errors["name"]     = "required"（66-67）
   - email 不合规          -> errors["email"]    = "invalid" （68-69）
     注意空邮箱走的是 "invalid"（email_is_invalid 对空串返回 True，
     cli.py:28-29），name/position 才有 required 分支。
   - position strip 后为空 -> errors["position"] = "required"（70-71）
   - errors 非空：emit_error(errors) 输出到 stderr 后 return 2
     （cli.py:72-74），不执行 INSERT——登记失败不新增记录。
   多字段错误合并为单个 JSON 对象，不会只报第一个。
   [文档] README:30-33 的 required/invalid、合并、退出码 2、不写入
   表述与代码一致。
   [测试] test_add_registration.py:184-200 覆盖三类单字段错误，
   :202-215 覆盖三字段同时错误，:218-247 断言空库上各类失败登记后
   候选人总数仍为 0（未运行）。

4. 邮箱规则 email_is_invalid(email)（cli.py:26-39，入参为已 strip 的
   邮箱），逐条返回 True（即 invalid）：
   1. 空串（cli.py:28-29）
   2. 含任意内部空白字符 ch.isspace()（cli.py:30-31）
   3. "@" 数量不等于 1（cli.py:32-33）
   4. 以唯一 @ 切分后 local 或 domain 为空（cli.py:34-36）
   5. domain 不含 "."，或以 "." 开头/结尾（cli.py:37-38）
   其余通过（cli.py:39）。规则之外不做任何检查：不校验域名后缀、
   不查 MX，"+"、多个点号、重复邮箱一律允许（email 列无 UNIQUE，
   cli.py:13-17；INSERT 前无查重）。
   [测试] test_add_registration.py:32-44 列出 11 种不合规输入，
   :196-200 逐一断言 invalid；:123-146 断言相同资料（含相同邮箱）
   可重复登记且各得不同 id（未运行）。

5. 保存（cli.py:76-81）：
     INSERT INTO candidates (name, email, position, stage)
     VALUES (?, ?, ?, ?)  绑定 (name, email, position, STAGE_APPLIED)
     conn.commit()
   - id 不由用户提供，由 candidates.id 的 AUTOINCREMENT 生成
     （cli.py:12），回显取 cursor.lastrowid（cli.py:84）。
   - stage 恒为常量 STAGE_APPLIED = "applied"（cli.py:7，绑定于
     cli.py:79）；add 解析器没有 --stage（cli.py:340-344），登记时
     阶段不可由输入指定。库里出现 interviewing 等其他值只能来自
     范围外的 set-stage（见第十节）。
   - 保存的 name/email/position 均为 strip 后的输入。

6. 成功输出（cli.py:83-91）：stdout 单行 JSON 对象，键序固定
   id, name, email, position, stage（dict 构造顺序，cli.py:83-89），
   json.dumps(..., ensure_ascii=False)（cli.py:90），中文不转义、
   使用默认分隔（": " 与 ", "），print 附加行尾换行；return 0。

四、查询流程 cmd_list（cli.py:94-133）
--------------------------------------------------------------------------------

1. 归一化，并以 None 区分“省略可选参数”与“显式空值”（cli.py:95-98）：
     position = args.position.strip()
     stage    = args.stage.strip() if args.stage is not None else None
     email    = args.email.strip() if args.email is not None else None
     name     = args.name.strip()  if args.name  is not None else None
   --position 在解析层必填（cli.py:347）；另外三个选项省略时为 None
   （cli.py:348-350），显式传入 "" 或纯空白时 strip 后为 ""。
   None 与 "" 在校验和拼 SQL 两个阶段都被区别对待。

2. 参数校验（cli.py:100-114），同样合并进一个 errors dict，键序为
   position → name → email → stage：
   - position 为空        -> "required"（cli.py:101-102）
   - name 显式提供且为空  -> "required"（cli.py:103-104）；
     省略（None）时不产生任何 name 错误。
   - email 显式提供且不合规（空串也算不合规）-> "invalid"
     （cli.py:105-106，复用 cli.py:26-39 的同一套规则）；省略不检查。
   - stage 显式提供时（cli.py:107-111）：为空 -> "required"
     （108-109）；非空但不在 STAGES = ("applied","interviewing",
     "hired","rejected")（cli.py:8）-> "invalid"（110-111）。
     因此 "offer"、大写 "INTERVIEWING" 均为 invalid；省略不检查。
   - errors 非空：emit_error(errors, compact=True) 后 return 2
     （cli.py:112-114），不执行 SELECT。
   [文档] README:35-42 对必传岗位、省略不过滤、四条件同时成立、
   显式空值 required、非法阶段/邮箱 invalid、多错误合并的描述与代码
   一致。
   [测试] test_list_filter.py:259-297 覆盖省略与显式空 stage 的区别、
   offer/大写阶段 invalid、空岗位、空岗位+offer 合并；
   test_list_name_filter.py:225-265 覆盖空姓名 required、空姓名+
   空岗位合并、空姓名+空 stage+坏邮箱三错误合并、省略 name 不触发
   name 错误（均未运行）。

3. 条件组合（cli.py:116-129）：四个条件全部以 AND 连接，岗位条件
   恒在，其余仅在“显式提供（strip 后仍非 None）”时追加：
     SELECT id, name, email, position, stage
       FROM candidates
      WHERE position = ?                              -- cli.py:116-117
      [AND name = ?]      name 非 None 时，cli.py:118-122
      [AND email = ?]     email 非 None 时，cli.py:123-125
      [AND stage = ?]     stage 非 None 时，cli.py:126-128
      ORDER BY id ASC                                  -- cli.py:129
   参数化绑定，无字符串拼接用户输入。
   - 岗位必填；姓名、邮箱、阶段省略时不限制该条件，提供时与岗位条件
     同时成立（AND，不是 OR）才算命中。
   - 重名记录全部返回：姓名只是普通等值条件，没有 DISTINCT/LIMIT
     （cli.py:116-130）。
   - 结果按 id 升序（cli.py:129 的 ORDER BY id ASC）。

4. 匹配语义：精确、区分大小写、内部空白有意义。
   [代码] 建表无 COLLATE 子句（cli.py:11-17），查询的 = 也不带
   COLLATE NOCASE / lower()（cli.py:121、124、127），使用 SQLite
   默认 BINARY 排序规则按 UTF-8 字节逐字节比较：英文字母大小写不同
   即不相等；strip 只作用于输入两端，库存值内部空格原样参与比较，
   单空格与双空格不可互换；无子串、无通配符匹配。
   [文档] README:14、36-38 明确“区分大小写、保留内部空白、不作子串
   或通配符匹配”，一致。
   [测试] test_list_filter.py:211-255（英文岗位大小写）、
   test_list_name_filter.py:274-334（英文姓名大小写、"Lin Xiao" 与
   "Lin  Xiao" 分别只命中各自记录、"Lin"/"Xiao" 子串返回 []）；未运行。

5. 两端空白的等价效果：查询词先 strip（cli.py:95-98），库存值在 add

1. emit_error(errors, compact=False)（cli.py:50-57）：
     separators = (",", ":") if compact else None
     print(json.dumps({"errors": errors}, ensure_ascii=False,
                      separators=separators), file=sys.stderr)
   - add 失败以默认 compact=False 调用（cli.py:73）：带空格的 JSON，
     形如 {"errors": {"name": "required", ...}}。
   - list 参数错误以 compact=True 调用（cli.py:113）：紧凑 JSON，
     形如 {"errors":{"name":"required","stage":"invalid"}}，
     ": " 与 ", " 处无空格（分隔规则 cli.py:53）；print 仍附加一个
     行尾换行。中文不转义（ensure_ascii=False，cli.py:55）。
   - 两种应用层错误共同约定：退出码 2、stdout 为空、单行、单个
     errors 对象、多字段错误合并。
   [测试] 紧凑格式有字节级断言：test_list_name_filter.py:231-241
   断言空姓名 + offer 阶段时 stderr 恰好为
   '{"errors":{"name":"required","stage":"invalid"}}\n'；
   add 的带空格格式见 test_add_registration.py:207-211。均未运行。

2. argparse 层错误（缺少必填选项）：缺少 --db、子命令、add 的

   SystemExit）；退出码同样是 2，但 stdout 为空、stderr 是用法说明
   文本而非 errors JSON，二者不要混淆。usage 的逐字文本依赖 Python

3. 副作用约定：
   - 登记失败不新增记录：return 2（cli.py:72-74）位于 INSERT
