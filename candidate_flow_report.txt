二、存储方式与表结构（SQLite，标准库 sqlite3）
--------------------------------------------------------------------------------

1. 存储确为本地 SQLite 文件：[代码] cli.py:4 `import sqlite3`，
   connect()，cli.py:42-47：
     conn = sqlite3.connect(db_path)
     conn.execute(SCHEMA)
     conn.commit()
   - sqlite3.connect 在文件不存在时创建新文件；SCHEMA 为
     CREATE TABLE IF NOT EXISTS，故每次调用幂等建表。[文档] README:7
     “首次操作时自动创建数据库文件与表”，与代码一致。

2. 本流程唯一使用的表 candidates（[代码] cli.py:10-18）：
     id       INTEGER PRIMARY KEY AUTOINCREMENT
     name     TEXT NOT NULL
     email    TEXT NOT NULL
     position TEXT NOT NULL
     stage    TEXT NOT NULL
   - 全部列 NOT NULL；除主键外没有 UNIQUE、CHECK、COLLATE 等任何其他约束
     [代码] 同上，建表语句中不存在这些子句。

3. 保存时机（add）：[代码] cli.py:76-81，业务校验全部通过后执行参数化
   INSERT，随后立即 conn.commit() 落盘；校验失败时在 cli.py:72-74 提前
   return，没有任何 INSERT 发生，即登记失败不新增记录。

4. 查询条件（list）：[代码] cli.py:116-129，SQL 以
     SELECT id, name, email, position, stage FROM candidates WHERE position = ?
   为基础，按提供的可选条件逐个拼接 AND name = ? / AND email = ? /
   AND stage = ?，最后 ORDER BY id ASC；全程参数化绑定。查询路径只有 SELECT，
   没有任何 INSERT/UPDATE/DELETE，即查询不改动任何记录（cli.py:94-133 全文）。

5. 保存后重新打开同一数据库文件仍能取回记录的机制（持久化依据）：
   [代码] 每次 `python -m recruiting` 都是新进程，main() 用同一 --db 路径
   重新 sqlite3.connect（cli.py:394）；CREATE TABLE IF NOT EXISTS 对已存在
   的表为空操作，add 时 commit 的行已写入该文件（cli.py:81），list 的
   SELECT 直接读出（cli.py:130）。持久化不依赖进程内存，只依赖同一文件路径。
   [测试] test_add_registration.py:106-121（add 进程结束后另起 list 进程读到
   同一条记录）、:123-146（重复登记后新 list 进程按 id 升序读到两条）；
   test_list_filter.py:188-197 与 test_list_name_filter.py:204-213（每次调用
   都是重新启动的命令，对同一数据库结果一致）。以上均为对测试源码的阅读
   结论，本报告未执行这些测试。

三、登记流程 cmd_add（cli.py:60-91）
--------------------------------------------------------------------------------

输入与归一化（cli.py:61-63）：
     name     = args.name.strip()
     email    = args.email.strip()
     position = args.position.strip()
  - 三个字段都做两端去空白（Python str.strip()），库存值与后续校验都基于
    去空白后的字符串。[文档] README:30 “字段两端空白会被去除”，一致。
  - 邮箱不做大小写转换，代码中不存在 lower/upper 调用；[文档] README:30
    “邮箱保留内部大小写”，与代码一致（strip 只去掉两端空白，内部字符原样）。

校验（cli.py:65-71），错误同时收集到同一个 dict：
  - name 去空白后为空     -> errors["name"]     = "required"（cli.py:66-67）
  - email 不合规（见下）  -> errors["email"]    = "invalid" （cli.py:68-69）
      注意：空邮箱走的是 "invalid" 而不是 "required"；代码里 name/position
      才有 required 分支。[文档] README:30-31 同为该表述。
  - position 去空白后为空 -> errors["position"] = "required"（cli.py:70-71）
  - errors 非空时：emit_error(errors) 输出到 stderr 后 return 2
    （cli.py:72-74），不执行 INSERT，不新增记录。
  - 多字段错误合并为单个 JSON 对象，键的插入顺序固定为 name、email、position
    [代码] 即上述三段判断的书写顺序（cli.py:65-71）。

错误输出格式（emit_error，cli.py:50-57）：
     print(json.dumps({"errors": errors}, ensure_ascii=False, separators=...),
           file=sys.stderr)
  - add 走默认分支（emit_error(errors)，cli.py:73）：separators=None，即
    json.dumps 默认的 ", " / ": " 带空格分隔；单行 JSON、中文不转义；
    stdout 不打印任何内容；退出码 2。
  - 紧凑分支（compact=True，separators=(",", ":")）只被 list 使用，见第四节。
  - [文档] README:30-33 描述与代码一致。

邮箱规则 email_is_invalid(email)（cli.py:26-39，入参为已 strip 的邮箱），
逐条返回 invalid 的条件：
  1. 空串（cli.py:28-29）
  2. 含任意内部空白字符 ch.isspace()（cli.py:30-31；两端空白已在调用前 strip）
  3. "@" 数量不等于 1（cli.py:32-33）
  4. 以唯一 @ 切分后 local 或 domain 为空（cli.py:34-36）
  5. domain 不含 "."，或以 "." 开头/结尾（cli.py:37-38）
  其余情况通过。规则之外不做任何检查（见第六节“未检查项”）。

成功写入（cli.py:76-81）：
     INSERT INTO candidates (name, email, position, stage)
     VALUES (?, ?, ?, ?)  绑定 (name, email, position, STAGE_APPLIED)
     conn.commit()

成功保存的字段：
  - name     ：去空白后的输入
  - email    ：去空白后的输入（内部大小写、内部点号等原样保留）
  - position ：去空白后的输入
  - stage    ：固定写入常量 STAGE_APPLIED = "applied"（cli.py:7，使用点
               cli.py:79、88）。登记生成记录的初始阶段恒为 applied。
  - id       ：不由用户提供，由 candidates.id 的 AUTOINCREMENT 生成
               （建表 cli.py:12），回显取 cursor.lastrowid（cli.py:84）。

招聘阶段在登记路径中的真实来源：
  - 登记时阶段不可由输入指定：add 子解析器没有 --stage 参数（cli.py:340-343），
    永远写入 cli.py:7 的常量 "applied"。
  - STAGES = ("applied", "interviewing", "hired", "rejected")（cli.py:8）在
    add 中不被引用；在 list 中仅用于校验 --stage 的取值（cli.py:110）。
    即：仅凭 add/list 两个命令，库中记录的 stage 恒为 applied；非 applied
    阶段只能由不在本流程范围的 set-stage 写入（见第五节注记）。

记录标识的真实来源：
  - 仅 SQLite 自增主键 id（INTEGER PRIMARY KEY AUTOINCREMENT，cli.py:12），
    代码中没有另外生成 UUID/业务编号；成功输出中的 id 即 cursor.lastrowid
    （cli.py:84）。

成功输出（cli.py:83-91）：
  - stdout 打印单行 JSON 对象，键序固定为
    id, name, email, position, stage（dict 按 cli.py:83-89 的插入顺序序列化），
    ensure_ascii=False 中文原样输出；return 0（cli.py:91）。

四、按岗位叠加条件查询流程 cmd_list（cli.py:94-133）
--------------------------------------------------------------------------------

1. 省略与显式空值的区分（条件组合的前提）：
   [代码] cli.py:95-98
     position = args.position.strip()
     stage = args.stage.strip() if args.stage is not None else None
     email = args.email.strip() if args.email is not None else None
     name  = args.name.strip()  if args.name  is not None else None
   - --position 由 argparse 保证存在（cli.py:347 required=True），直接 strip。
   - --name/--stage/--email 省略时 argparse 给出 None，代码保留 None 表示
     “该条件不参与”；显式提供（包括显式空串）时先 strip 再进入校验。
   - 因此“省略可选参数”与“显式给空值”是两种不同输入：前者不过滤也不报错，
     后者按下一条报错。

2. 校验（cli.py:100-111），错误合并到同一个 dict：
   - position 去空白后为空            -> errors["position"] = "required"
     （cli.py:101-102）
   - name 已提供且去空白后为空        -> errors["name"]     = "required"
     （cli.py:103-104）
   - email 已提供且不合规（同第三节 email_is_invalid，含空串）
                                      -> errors["email"]    = "invalid"
     （cli.py:105-106）
   - stage 已提供：去空白后为空       -> errors["stage"]    = "required"
     （cli.py:107-109）；非空但不在 STAGES（cli.py:8）四值之内
                                      -> errors["stage"]    = "invalid"
     （cli.py:110-111）。比较是精确成员判断，大写形式（如 INTERVIEWING）
     与四值之外的形式（如 offer）同样 invalid。
   - errors 非空时：emit_error(errors, compact=True)（cli.py:112-114），
     return 2，不执行查询。
   - 键的插入顺序固定为 position、name、email、stage [代码] 即 cli.py:100-111
     的书写顺序。
   - 查询错误 JSON 为紧凑格式：compact=True 使 separators=(",", ":")
     （cli.py:53），输出无多余空白的单行 JSON，例如
     {"errors":{"name":"required","stage":"invalid"}}；与 add 的带空格格式
     不同（对照 cli.py:73 与 cli.py:113 两个调用点，及 cli.py:51-52 的注释）。
   - 业务校验失败时 stdout 为空、退出码为 2；缺少必填选项（如 list 不带
     --position）则走第一节第 3 点的 argparse 出口：同样退出码 2，但 stderr
     是用法说明而非 errors JSON。

3. 条件组合与查询（cli.py:116-130）：
     sql = "SELECT id, name, email, position, stage FROM candidates
            WHERE position = ?"           （cli.py:116）
     若 name  非 None：sql += " AND name = ?"  （cli.py:118-122）
     若 email 非 None：sql += " AND email = ?" （cli.py:123-125）
     若 stage 非 None：sql += " AND stage = ?" （cli.py:126-128）
     sql += " ORDER BY id ASC"                 （cli.py:129）
   - 岗位条件恒存在；姓名、邮箱、阶段省略时不限制结果，提供时各追加一个
     AND 条件，即所有提供的条件与岗位条件同时成立才算命中。
   - 全部为参数化绑定（params 列表 cli.py:117-128），无字符串拼接用户输入。

4. 匹配语义：精确匹配、区分大小写、内部空白有意义。
   [代码] SQL 是普通的 `=` 比较，列定义没有 COLLATE 子句（cli.py:11-17），
   查询也没有 COLLATE NOCASE / lower() / LIKE 等处理（cli.py:116-129），
   使用 SQLite 默认 BINARY 排序规则按字节完整比较：字节不同即不相等。
   由此（并见 cli.py:119-120 的注释）：
   - 姓名与邮箱均精确匹配且区分英文字母大小写；中文无大小写折叠，字面值
     不同即不匹配。
   - 姓名内部空白有意义：库存 "Lin  Xiao"（双空格）与查询 "Lin Xiao"
     （单空格）不相等；去两端空白不等于子串匹配，"Lin" 查不到 "Lin Xiao"。
   - 无唯一性约束（cli.py:10-18），同名（或同邮箱）记录全部返回。
   - 查询词先 strip（cli.py:95-98），库存值在 add 时也已 strip（cli.py:61-63），
     因此查询词两端的空白不影响命中，而内部空白逐字节参与比较。
   [文档] README:35-42 与上述一致。

5. 输出（cli.py:130-133）：
     rows -> [dict(zip(FIELDS, row)) ...]（FIELDS 见 cli.py:20，键序
     id, name, email, position, stage），stdout 打印 JSON 数组
     （json.dumps(..., ensure_ascii=False)，默认带空格分隔），return 0。
   - 多条命中按 id 升序排列（ORDER BY id ASC，cli.py:129）。
   - 未命中：fetchall() 得到空列表，stdout 恰好打印 []，return 0
     （cli.py:130-133）。不是错误：stderr 无输出、退出码为 0。
   - 输出中 stage 字段直接读自表列；查询路径不计算、不改写任何记录
     （cli.py:94-133 中只有 SELECT）。

6. 与 add 的关系小结：add 负责“strip → 校验 → INSERT+commit → 对象输出”，
   list 负责“strip（可选条件保留 None）→ 校验 → 组合 WHERE → 数组输出”；
   两者共用同一 --db 文件、同一张 candidates 表、同一套邮箱规则与
   emit_error（格式分支不同），这就是“登记保存的合成资料能被同一数据库的
   查询读回”的全部机制。
