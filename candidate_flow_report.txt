三、登记流程 cmd_add（cli.py:51-82）
--------------------------------------------------------------------------------

输入与归一化（cli.py:52-54）：
     name     = args.name.strip()
     email    = args.email.strip()
     position = args.position.strip()
  - 三个字段都做两端去空白（Python str.strip()），库存值与后续校验都基于
    去空白后的字符串。[文档] README:21 “字段两端空白会被去除”，一致。
  - 邮箱不做大小写转换，代码中不存在 lower/upper 调用；[文档] README:21-22
    “邮箱保留内部大小写”，与代码一致（strip 只去掉两端空白）。

校验（cli.py:56-65），错误同时收集到同一个 dict：
  - name 去空白后为空     -> errors["name"]     = "required"（cli.py:57-58）
  - email 不合规（见下）  -> errors["email"]    = "invalid" （cli.py:59-60）
      注意：空邮箱走的是 "invalid" 而不是 "required"；代码里 name/position
      才有 required 分支。[文档] README:21-22 同为该表述。
  - position 去空白后为空 -> errors["position"] = "required"（cli.py:61-62）
  - errors 非空时：emit_error(errors) 输出到 stderr 后 return 2
    （cli.py:63-65），不执行 INSERT。
  - 多字段错误合并为单个 JSON 对象，键的插入顺序固定为 name、email、position
    [代码] 即上述三段判断的书写顺序。

错误输出格式（emit_error，cli.py:47-48）：
     print(json.dumps({"errors": errors}, ensure_ascii=False), file=sys.stderr)
  - 单行 JSON、中文不转义；stdout 不打印任何内容；退出码 2。
  - [文档] README:22-24 描述与代码一致。

邮箱规则 email_is_invalid(email)（cli.py:23-36，入参为已 strip 的邮箱），
逐条返回 invalid 的条件：
  1. 空串（cli.py:25-26）
  2. 含任意内部空白字符 ch.isspace()（cli.py:27-28；两端空白已在调用前 strip）
  3. "@" 数量不等于 1（cli.py:29-30）
  4. 以唯一 @ 切分后 local 或 domain 为空（cli.py:31-33）
  5. domain 不含 "."，或以 "." 开头/结尾（cli.py:34-35）
  其余情况通过。规则之外不做任何检查（见第六节“未检查项”）。

成功写入（cli.py:67-72）：
     INSERT INTO candidates (name, email, position, stage)
     VALUES (?, ?, ?, ?)  绑定 (name, email, position, STAGE_APPLIED)
     conn.commit()

成功保存的字段：
  - name     ：去空白后的输入
  - email    ：去空白后的输入（内部大小写、内部点号等原样）
  - position ：去空白后的输入
  - stage    ：固定写入常量 STAGE_APPLIED = "applied"（cli.py:7，使用点 cli.py:70）
  - id       ：不由用户提供，由 candidates.id 的 AUTOINCREMENT 生成
               （建表 cli.py:11-12），回显取 cursor.lastrowid（cli.py:75）

招聘阶段在当前代码中的真实来源：
  - 登记时阶段不可由输入指定：add 子解析器没有 --stage 参数（cli.py:139-143），
    永远写入 cli.py:7 的常量 "applied"。
  - STAGES = ("applied", "interviewing", "hired", "rejected")（cli.py:8）在
    add/list 路径中完全不被引用；它只被 set-stage 使用（cli.py:110），而
    set-stage 不在本次追踪范围。即：其余三个阶段在本流程中无来源。

记录标识在当前代码中的真实来源：
  - 仅 SQLite 自增主键 id（INTEGER PRIMARY KEY AUTOINCREMENT，cli.py:11-12），
    代码中没有另外生成 UUID/业务编号；成功输出中的 id 即 cursor.lastrowid
    （cli.py:75）。

成功输出（cli.py:74-82）：
  - stdout 打印单行 JSON 对象，键序固定为
    id, name, email, position, stage（dict 按 cli.py:74-80 的插入顺序序列化），
    ensure_ascii=False 中文原样输出；return 0。

四、按岗位查询流程 cmd_list（cli.py:85-98）
--------------------------------------------------------------------------------

1. 归一化与校验：
     position = args.position.strip()（cli.py:86）
     去空白后为空 -> stderr {"errors": {"position": "required"}}，return 2
     （cli.py:87-89），不执行查询。

2. 查询与输出（cli.py:91-98）：
     SELECT id, name, email, position, stage
       FROM candidates WHERE position = ? ORDER BY id ASC
     rows -> [dict(zip(FIELDS, row)) ...]（FIELDS 见 cli.py:20，列名与键名一致）
     stdout 打印 JSON 数组（json.dumps(..., ensure_ascii=False)），return 0。

3. 大小写是否区分：区分。
   [代码] SQL 是普通的 `=` 比较，列定义没有 COLLATE 子句（cli.py:11-18），
   查询也没有 COLLATE NOCASE / lower() 等处理（cli.py:91-95），使用 SQLite
   默认 BINARY 排序规则按字节比较：字节不同即不相等（对 ASCII 大小写表现为
   区分大小写；中文无大小写折叠，字面值不同即不匹配）。
   [文档] README:14 明确“区分大小写”，与代码一致。

4. 首尾空白：查询词先 strip（cli.py:86），而库存岗位在 add 时也已 strip
   （cli.py:54），因此 `list --position " 测试工程师 "` 与库存的
   "测试工程师" 相等可命中；库存中不会因公开登记路径而保留两端空白。

5. 没有匹配记录时的返回：
   [代码] fetchall() 得到空列表，json.dumps([]) 打印 `[]` 到 stdout，
   return 0（cli.py:95-98）。不是错误：stderr 无输出、退出码为 0。

6. 输出中 stage 字段直接读自表列（cli.py:92、96）；本流程登记的行该列恒为
   applied（第三节），查询路径本身不计算或改写阶段。

以下情形在 add/list 路径中没有任何校验或分支，静态依据为“对应代码不存在”：
  1. 邮箱重复：candidates.email 无 UNIQUE 约束（cli.py:10-18），cmd_add 在

  3. 邮箱在第五节五条规则之外不再检查：不校验域名后缀、不查 MX、含 "+"、
     多个点号等一律通过（cli.py:23-36 是全部规则）。
  4. list 只按岗位精确相等过滤：无姓名/邮箱/stage 过滤、无模糊匹配、无分页、
     无全量列表入口（--position 必填，cli.py:146；SQL 见 cli.py:91-95）。
  5. 数据库层面的运行期异常（--db 路径不可写、文件损坏、磁盘错误等）代码不
     捕获：main 只有 try/finally 关闭连接，没有 except（cli.py:157-163），
     sqlite3 异常将以 Python 回溯形式抛出，回溯文本与退出码（未捕获异常通常
     为 1）[无法确认] 于不运行时逐字给出；README 也未文档化此类情形。
