二、如何确定目标：编号只定位 feedback 表的主键
--------------------------------------------------------------------------------

1. 编号先去除两端空白，再按 ASCII 正整数校验
   [代码] recruiting/cli.py:454-456 调用 args.feedback_id.strip()；
   校验函数 validate_candidate_id 在 cli.py:147-155：
     if not re.fullmatch(r"[0-9]+", candidate_id) or int(candidate_id) < 1:
         return "invalid", None                       # cli.py:153-154
     return None, int(candidate_id)                   # cli.py:155
   由此可直接推出：
   - 允许且仅允许 ASCII 数字 0-9 组成的非空串（字符类 [0-9] 不含全角
     数字，re.fullmatch 要求整串匹配）；
   - 允许前导零（"0002" 正则通过，int("0002") == 2）；
   - int(...) < 1 即全零被拒（"0"、"000"）；
   - 负数 "-1"、带正号 "+1"、小数 "1.5" 均无法整串匹配 [0-9]+；
   - 两端空白在 strip 阶段去除，"  0002  " 合法；内部空白使整串匹配
     失败；空串与纯空白 strip 后为空串，正则不匹配。
   [文档] README.md:122-124 的规则表述与代码一致。

2. 非法编号返回 feedback_id 的 invalid（退出码 2，不发生写入）
   [代码] cli.py:457-459：
     emit_error({"feedback_id": feedback_id_error})
     return 2
   emit_error 把 {"errors": ...} 输出到 stderr（cli.py:61-68）。此时
   程序尚未查询或修改 feedback 表。

3. 编号是“评价编号”，即使数值与候选人 id 相同也只定位评价
   [代码] find_feedback（cli.py:384-405）的查询语句是
     SELECT id, candidate_id, text FROM feedback WHERE id = ?
   （cli.py:397-400），查询对象是 feedback 表的主键 id，与
   candidates 表无任何关联条件；cmd_delete_feedback 全程不查询
   candidates 表。因此编号 2 命中的是 feedback.id = 2 那一行，该行
   的 candidate_id 是多少就返回多少，与是否存在 candidates.id = 2
   无关。文字内容同样不参与定位：两条文字完全相同的评价各有独立
   主键，删除只作用于指定编号那一条。
   [文档] README.md:120-122 明确“取自已有评价结果，不是候选人编号，
   即使编号数值与某位候选人 id 相同也只定位评价”。
   [测试] test_feedback.py:476-486（test_delete_returns_original_record）
   构造候选人 id 2（周宁）存在、评价 id 2 属于候选人 1（林晓）的局面，
   断言删除返回的 candidate_id 为 1，且断言 self.zhou_ning["id"] == 2
   （test_feedback.py:482）；本文件未运行该测试。

4. 合法但不存在：not_found
   [代码] find_feedback 在 cli.py:393-395 先拦截超过 SQLite 有符号
   64 位整数上限的编号（SQLITE_INT64_MAX = 9223372036854775807，
   cli.py:34），直接按 not_found 处理，避免参数绑定溢出；
   cli.py:397-403 执行主键查询，fetchone() 为 None 时输出
   {"feedback_id": "not_found"} 并返回 None。调用方
   cli.py:461-463 据此 return 2，DELETE 不执行。
   故“库里从未有过的编号”“已删除的编号”“9223372036854775808”
   三者结果相同。
   [测试] test_feedback.py:571-574（999）、576-580
   （9223372036854775808）、521-532（删后再删同一编号）；未运行。

三、如何保存结果：先取原行，再删除提交，返回删除前的原对象
--------------------------------------------------------------------------------

1. feedback 表结构与编号生成
   [代码] recruiting/cli.py:24-28：
     CREATE TABLE IF NOT EXISTS feedback (
         id INTEGER PRIMARY KEY AUTOINCREMENT,
         candidate_id INTEGER NOT NULL,
         text TEXT NOT NULL
     )
   id 为 INTEGER PRIMARY KEY AUTOINCREMENT（cli.py:25）。删除一行不会
   把其编号放回编号池：SQLite 对 AUTOINCREMENT 表在内部
   sqlite_sequence 中单调递增，后续追加由 add-feedback 的 INSERT
   （cli.py:351-354）取得新的 lastrowid，不复用已删除编号。
   [文档] README.md:132-134 明确“AUTOINCREMENT 继续递增”。
   [测试] test_feedback.py:546-557 断言删除编号 2 后再追加，新编号
   大于编号 3，列表为 [编号1, 新记录]；未运行。

2. 删除与提交
   [代码] recruiting/cli.py:465-466：
     conn.execute("DELETE FROM feedback WHERE id = ?", (feedback_id_int,))
     conn.commit()
   参数化绑定，按主键恰好删除一行；提交后对后续所有进程生效。
   DELETE 不触碰 candidates、stage_history 表，也不重算任何统计
   （summary 实时从 candidates 表分组计数，见 cli.py:521-533）。

3. 返回的是“被删记录的原对象”，取自删除前的 SELECT 行
   [代码] find_feedback 的 SELECT 在 DELETE 之前执行（cli.py:397-400
   早于 cli.py:465）；cmd_delete_feedback 用该行 row 组装：
     record = {"id": row[0], "candidate_id": row[1], "text": row[2]}
     print(json.dumps(record, ensure_ascii=False))
     return 0
   （cli.py:467-469）。即输出的是删除前库存内容，不是删除后的状态
   （删除后该行已不存在）。对象仅含 id、candidate_id、text 三个
   字段；json.dumps 默认分隔符使 ": " 与 ", " 处带空格，
   ensure_ascii=False 使中文原样输出，print 追加恰好一个行尾换行。

4. 内部换行通过 JSON 转义保留在单行中
   [代码] 库存文本在写入时只去两端空白、内部换行原样保存
   （validate_feedback_text，cli.py:307-317；add-feedback 绑定于
   cli.py:351-354）。删除成功输出走 json.dumps（cli.py:468），库存的
   U+000A 换行被序列化为两个字符的反斜杠+n（\n），因此 stdout 物理
   上只有一行，解析回 JSON 后文本中的换行仍然存在。
   [测试] test_feedback.py:488-500 断言返回文本逐字等于含换行的
   原文本、且 stdout 字符串中包含字面两字符 "\\n"；另由
   test_feedback.py:466-474 的断言（stderr 为空、stdout 按
   splitlines 只有一行、字段集合恰为三项）约束输出形态；均未运行。

四、对后续查询与其他数据的影响
--------------------------------------------------------------------------------

1. list-feedback：少一行，其余行的编号、文字、归属与升序不变
   [代码] cmd_list_feedback（cli.py:365-381）只做

      WHERE candidate_id = ? ORDER BY id ASC

   评价因 candidate_id 条件不命中而完全不变。查询本身无任何写入。

   [代码] 候选人存于 candidates 表（cli.py:11-17），DELETE 语句只
   针对 feedback 表（cli.py:465），不删除候选人。目标候选人再查
   list-feedback 时 fetchall 为空，输出 []（cli.py:376-380）；get
   仍能从 candidates 表读到该候选人（cmd_get，cli.py:240-251）。
   [文档] README.md:130-131。
   [测试] test_feedback.py:502-509 断言删除周宁唯一评价后
   list-feedback 为 [] 而 get 周宁仍成功；未运行。

3. 持久化：重开同一数据库后删除仍生效
   [代码] DELETE 后立即 commit（cli.py:466）；新进程以同一 --db
   重新 sqlite3.connect（cli.py:680、55），已提交的删除就是文件的
   当前状态，无需任何额外初始化。
   [测试] test_feedback.py:511-519 用两次独立命令调用断言结果一致；
   未运行。

4. 删后对同一编号的操作按“评价不存在”处理
   [代码] 再次 delete-feedback：find_feedback 查询落空，返回
   not_found（cli.py:401-403 → 461-463）。set-feedback 更正同一
   编号也共用 find_feedback（cli.py:430-432），同样 not_found，

5. 不影响候选人资料、阶段历史与岗位统计

   stage_history（cli.py:18-23）表无语句触及；summary 从
   candidates 实时 COUNT 分组（cli.py:521-533），行数未变故统计
   不变。失败路径（cli.py:457-463 的 return 2）更在 DELETE 之前，
   任何表都不改动。
   [测试] test_feedback.py:582-603 在一串 invalid/not_found 失败

插入；编号相等（都有 2）只是数值巧合，两条命令的定位表不同。

主操作（题目指定的完整示例）：
  python -m recruiting --db demo.sqlite3 delete-feedback --feedback-id 2

[实跑] 退出码 0；标准错误为空；标准输出为单行 JSON（行尾一个换行）：

位，删除的只是编号 2 这一条。

删除后的查询命令：
  python -m recruiting --db demo.sqlite3 list-feedback --id 1
  python -m recruiting --db demo.sqlite3 list-feedback --id 2

即候选人 1 只剩评价 1 的原对象；周宁及其评价 3 原样保留。

  （上面 summary 为便于阅读折行，实际 stdout 为单行。）

[实跑] 持久化与后续编号（新进程重开同一数据库）：
  再次 list-feedback --id 1 / --id 2：与上面完全一致（删除已落盘）。
  再次 delete-feedback --feedback-id 2：
    rc=2，stdout 为空，stderr 单行：
