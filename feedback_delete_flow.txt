================================================================================
二、一次删除如何“确定目标”
================================================================================

1. 只取一个参数 --feedback-id，先去两端空白
   [代码] recruiting/cli.py:454-456：
       feedback_id_error, feedback_id_int = validate_candidate_id(
           args.feedback_id.strip()
       )
   即编号先做 str.strip()；两端空白被忽略，内部字符原样进入校验。

2. 编号合法性由 validate_candidate_id 判定 [代码]
   recruiting/cli.py:147-155：
       if not re.fullmatch(r"[0-9]+", candidate_id) or int(candidate_id) < 1:
           return "invalid", None
       return None, int(candidate_id)
   - 必须整体（fullmatch）由 ASCII 数字 [0-9] 组成，且转成整数后 >= 1。
   - 因此接受：含前导零的 ASCII 正整数（"2"、"02"、"0002" 都解析为 2）。
   - 拒绝 invalid：空串/纯空白（strip 后为空，fullmatch 失败）、全零
     "0"/"000"（int 后 <1）、负数 "-1"、带正号 "+1"、小数 "1.5"
     （正则不接受 '-' '+' '.'）、全角数字 "１２"（不在 ASCII [0-9]）。
   该函数名虽为 candidate_id，但被评价相关命令复用；delete-feedback 在
   recruiting/cli.py:454 调用它解析的是 feedback_id。

3. 编号即使与某位“候选人 id”数值相同，也只定位“评价”
   [代码] recruiting/cli.py:397-400 的查找语句查的是 feedback 表：
       SELECT id, candidate_id, text FROM feedback WHERE id = ?
   整条删除流程从不查询 candidates 表来决定删哪条；candidate_id 只是被
   命中评价行里带回的归属列。因此 --feedback-id 2 的含义是“评价主键 id=2”，
   与“候选人 id=2 是否存在”无关。
   [文档] README.md:120-122 “按评价编号（取自已有评价结果，不是候选人
   编号，即使编号数值与某位候选人 id 相同也只定位评价）”，与代码一致。
   [测试] test_feedback.py:476-486（test_delete_returns_original_record）
   显式断言候选人 2（周宁）存在，但删除编号 2 返回的 candidate_id 是
   林晓的 id；set-feedback 侧同义断言见 test_feedback.py:326-329。

4. 同文评价也只删除指定记录：定位条件只有主键 id = ?（等值、参数化），
   不按 text 匹配，也没有 LIMIT 之外的批量删除。
   [代码] recruiting/cli.py:397-400（按 id 取唯一行）、465
   （DELETE ... WHERE id = ?）。故两条 text 完全相同的评价，删 id=2 只删
   id=2 那一条，id=1 原样保留。[实测] 见第四节示例 2/示例 3。

5. int64 上限与“合法但不存在”
   find_feedback [代码] recruiting/cli.py:384-405：
     - feedback_id_int > SQLITE_INT64_MAX（常量 9223372036854775807，
       recruiting/cli.py:34）时，直接 emit {"feedback_id":"not_found"}
       并返回 None（393-395），注释说明这是为了避免绑定参数时抛
       OverflowError。故 9223372036854775808 归为 not_found 而非 invalid。
     - 否则在 feedback 表按 id 查行（397-400）；fetchone() 为 None 时
       emit {"feedback_id":"not_found"}（401-403）。
   合法但当前不存在的编号（如 999、已删除的编号）都走这一支。


================================================================================
三、删除如何“保存结果”
================================================================================

1. 真正的删除与落盘 [代码] recruiting/cli.py:465-466：
       conn.execute("DELETE FROM feedback WHERE id = ?", (feedback_id_int,))
       conn.commit()
   - 参数化绑定（无用户输入拼接到 SQL）。
   - DELETE 在“校验通过 + 已查到行”之后才执行；任何错误出口都在此之前
     return 2，故失败不产生删除、不需要回滚（见 457-463）。
   - 紧接 conn.commit() 落盘，因此删除在进程结束、重开数据库后仍生效。

2. 返回的是“被删记录的原对象”，且取自删除前查到的行
   [代码] recruiting/cli.py:461 先把行读入 row，465 才删除，467 用 row
   组装结果：
       record = {"id": row[0], "candidate_id": row[1], "text": row[2]}
       print(json.dumps(record, ensure_ascii=False))
   - 仅含 id、candidate_id、text 三个字段（467），键序即此构造顺序。
   - text 是保存时的原文：add-feedback 写入前会 strip 两端空白、保留内部
     空白/换行（validate_feedback_text，recruiting/cli.py:307-317；
     插入在 351-354），delete 不再做任何裁剪，只原样回显。
   - json.dumps(..., ensure_ascii=False)：中文不转义；文本里的内部换行符
     被 JSON 转义成字面两字符反斜杠+n（"\\n"），因此整条结果仍是单行，
     不会被换行拆成多行（468）。
   [测试] 单行与转义：test_feedback.py:466-474（assert_delete_success 断言
   stdout.splitlines() 恰为 1 行、字段集合恰为三项）、488-500（含 "\\n"
   与逐字文本）。

3. 成功输出契约 [代码] recruiting/cli.py:467-469 + print 默认行为：
   - 标准输出：单行 JSON 对象 + 一个行尾换行（print）。
   - 标准错误：为空（成功路径不调用 emit_error）。
   - 退出码：0（return 0，469）。
   [文档] README.md:128-131 与之一致。
   [实测] 见第四节示例 2、附录 B 各 rc=0 项（stderr 均为空串）。

4. 字段错误输出契约（失败时）[代码] emit_error 定义于
   recruiting/cli.py:61-68：
       print(json.dumps({"errors": errors}, ensure_ascii=False,
                        separators=separators), file=sys.stderr)
   delete-feedback 以默认 compact=False 调用（458、394、402），故错误
   JSON 带默认空格，形如 {"errors": {"feedback_id": "invalid"}}；只写
   stderr，stdout 不打印任何内容，返回退出码 2。
   [实测] stderr 逐字为 '{"errors": {"feedback_id": "invalid"}}\n'，
   stdout 为 ''（见附录 B b01-b11）。

5. 缺少 --feedback-id 的出口与上面不同：由 argparse 处理，不进入
   cmd_delete_feedback。参数 required=True（recruiting/cli.py:645），
   parse_args（679）直接向 stderr 打印 usage 用法说明并以退出码 2 终止，
   stdout 为空。[实测] 见附录 B b14（usage 跨两行、含 "usage:" 字样，
   不是 errors JSON）。
   [测试] test_feedback.py:605-609 断言 returncode==2、stdout 为空、
   stderr 含 "usage"。

说明：以下示例在“同一个”全新数据库 demo.sqlite3 上顺序执行，以保证

（README.md:11 的用法），输出相同。前置数据全部为合成资料：

  候选人 1：name="林晓"  email="lin.xiao@example.test"
            position="测试工程师"  stage="applied"（add 固定写入）
  候选人 2：name="周宁"  email="zhou.ning@example.test"
            position="测试工程师"  stage="applied"

  预期 / 实际完全一致：
    退出码：0

================================================================================
五、删除对后续查询与其它数据的影响
================================================================================

1. list-feedback：少一条，其余的编号/文字/归属/升序不变
   [代码] recruiting/cli.py:365-381（只读 SELECT，WHERE candidate_id=?
   ORDER BY id ASC）。删除评价 2 后 [实测]：
     list-feedback --id 1 -> 只剩 [评价1]（示例 3）；
     list-feedback --id 2 -> 仍是 [评价3]。
   [测试] test_feedback.py:484-486、530-532、554-557。

2. 候选人资料不变：delete-feedback 只 DELETE feedback 表
   （recruiting/cli.py:465），不写 candidates 表。删除前后 get 结果逐字
   一致 [实测]：
     get --id 1 -> {"id": 1, ..., "stage": "applied"}（前后相同）
     get --id 2 -> {"id": 2, ..., "stage": "applied"}（前后相同）
   特别地，删掉某人最后一条评价后，候选人仍存在（见第七节第 3 点）。

3. 阶段历史不变：delete-feedback 不触碰 stage_history 表。
   [实测] 删除前后 stage-history --id 1 均为 []。
   [测试] test_feedback.py:597-599（删除类失败场景下历史仍为 []）。
   [推导] 本例两名候选人从未 set-stage 成不同阶段，历史本就为空；删除
   评价不会新增或删除历史（cmd_delete_feedback 内无 stage_history 写入，
   recruiting/cli.py:444-469）。

4. 岗位统计不变：summary 只读 candidates 并按 position/stage 分组
   [代码] recruiting/cli.py:521-533、572-586；feedback 行数不参与统计。
   [实测] 删除 2 前后 summary --position "测试工程师" 逐字一致：
     {"position": "测试工程师", "total": 2,
      "counts": {"applied": 2, "interviewing": 0, "hired": 0, "rejected": 0}}
   [测试] test_feedback.py:586、600-603（删除失败不改变统计的断言）。

5. 对 set-feedback 的影响：被删编号再更正按“评价不存在”处理。
   [代码] set-feedback 同样先 find_feedback（recruiting/cli.py:430），
   已删除行 fetchone 为 None -> not_found（401-403）。
   [实测] 删除评价 3 后执行
     set-feedback --feedback-id 3 --text "新文字"
   -> rc=2，stdout 空，stderr：
     {"errors": {"feedback_id": "not_found"}}
   [测试] test_feedback.py:534-544。

6. 对 add-feedback 的影响：后续追加得到“新的、更大的”主键，不复用被删
   编号（详见第七节第 4 点）。

7. 失败操作零副作用：invalid/not_found 都在 DELETE（465 行）之前返回，
   不改动任何评价、候选人、历史或统计。[测试] test_feedback.py:582-603
   在一连串非法/不存在调用后断言两类查询与 get/history/summary 快照不变；
   [实测] 见第六节边界表后的 b12/b13 复查。


================================================================================
六、编号规则与失败边界
================================================================================

合法形式（去两端空白后）[代码] recruiting/cli.py:153 的
re.fullmatch(r"[0-9]+", ...) 且 int(...) >= 1：
  - "2"、"02"、"0002"、"  2  "（strip 后为 "2"）、"  0003  " 都合法，
    归一为同一个整数主键。[实测] "  0003  " 成功删除评价 3（附录 B #30）。
  - 注意：前导零只影响“能否解析”，不改变定位的整数；不存在“02 号评价”
    与“2 号评价”两条记录。

失败分三类，出口不同：

(A) feedback_id = invalid —— 语法层不合法

================================================================================
七、持久化、删空、重复删除与编号不复用
================================================================================

1. 重开同一数据库后删除仍生效（持久化）
   机制：成功删除后立即 conn.commit()（recruiting/cli.py:466）；每次
   `python -m recruiting` 都是独立进程，main 以同一 --db 重新
   sqlite3.connect（680；connect 在 53-58），建表用 CREATE TABLE IF NOT
   EXISTS（SCHEMA，10-29；executescript 在 56）对已存在的表是空操作，
   已提交的 DELETE 结果保留在文件中。
   [实测] 删除 2、3 并追加评价 4 后，用“新的一次进程”再次查询：
     list-feedback --id 1 -> [评价1, 评价4]
     list-feedback --id 2 -> []
   与删除当次结果逐字一致。
   [测试] test_feedback.py:511-519（两次独立调用结果一致）。
   [文档] README.md:131-132。

2. 再次删除同一编号 -> not_found
   [代码] 第二次执行时 feedback 表已无该行，find_feedback 走 401-403。
   [实测] 成功删评价 2 后再删一次 2：rc=2、stdout 空、stderr
   {"errors": {"feedback_id": "not_found"}}；且这次失败不动其余记录
   （评价 1、3 复查不变）。[测试] test_feedback.py:521-532。

3. 最后一条评价被删后：查询为 []，但候选人仍存在
   [实测] 用 "  0003  " 删除周宁唯一的评价 3 后：
     list-feedback --id 2 -> []（退出码 0，非错误）
     get --id 2           -> 仍是周宁的候选人对象（id=2，applied）
   [代码] list-feedback 对“候选人存在但无评价”返回空数组：
   recruiting/cli.py:371-380（fetchall 为空 -> records=[] -> 打印 []）；
   delete 只删 feedback（465），candidates 行保留。
   [测试] test_feedback.py:502-509。
   [文档] README.md:130-131。

4. 后续追加不复用已删编号（AUTOINCREMENT 继续递增）
   [代码] feedback 主键为 INTEGER PRIMARY KEY AUTOINCREMENT
   （recruiting/cli.py:24-28）。SQLite 对 AUTOINCREMENT 在内部
   sqlite_sequence 表记录单调游标，删除行不会回退，故新插入取更大值。
   [实测] 删除 2、3 之后再为林晓追加一条：
     add-feedback --id 1 --text "新评价"
     -> {"id": 4, "candidate_id": 1, "text": "新评价"}
   新 id=4 > 已存在过的最大 id 3，没有复用被删的 2 或 3；随后
     list-feedback --id 1 -> [评价1, 评价4]（按 id 升序）
   底层佐证 [实测]：直接只读查询该库，
     sqlite_sequence 中 feedback 的 seq=4，
     feedback 表实际行为 (1,1,'表达清楚') 与 (4,1,'新评价')，
     candidates 仍为 1 林晓、2 周宁，stage_history 为空。
   [测试] test_feedback.py:546-557（断言新 id 大于第三人评价 id，
   列表为 [first, new_record]）。
   [文档] README.md:132-134（明确“不复用已删除编号（AUTOINCREMENT
   继续递增）”）。

5. 其余评价及候选人资料、阶段历史、岗位统计均不变
   汇总 [实测]：删除 2 与删除 3 两组操作后——
     - 未被点名的评价（评价 1，以及各自时点的评价 3/1）编号、文字、
       candidate_id 归属、升序位置均不变；
     - get 两名候选人结果与删除前逐字一致；
     - stage-history 仍为 []；
     - summary "测试工程师" 仍为 total=2、applied=2 其余 0。
   源码依据：cmd_delete_feedback 仅有一条针对 feedback 表单行的
   DELETE（recruiting/cli.py:465），无其它表写操作（444-469）。
   [文档] README.md:134-135。
